PART 0 — Executive layer

1. What Aonex is

Aonex is a multi-marketplace product-catalog ingestion & distribution platform. A client hands us product data from wherever it lives — a marketplace URL, a CSV export, or a live store connector (Shopify, eBay) — and we turn messy, inconsistent, multi-source reality into one clean, deduplicated, trustworthy catalog the client can distribute to any channel.

The four hard problems we solve: extract correct fields from any source; resolve identity (is this the same physical product we already have, from another marketplace?); decide readiness (is it complete and trustworthy enough to publish?); and give humans the tools to finish what the machine can't.

2. The bet (one slide)

Permissive intake, strict publish — on a GTIN/identity spine. Accept almost anything; resolve identity aggressively (backfilling the universal GTIN key); score completeness against what the product's type needs; gate only at publish; auto-merge only on a strong, corroborated key (everything else is a human-confirmed proposal). Today the system does the opposite (strict 5-field intake gate, identity that only fires when a GTIN happens to be present) — which is why incomplete-but-valid products dead-end and the same product duplicates across marketplaces.

PART 1 — Core concepts (shared)

6. The canonical data model — observations & the golden record

The heart of the system is that we never store "the price is ₹79,999." We store "source croma:link observed price ₹79,999 at time T with confidence 0.93." Every attribute is an append-only stream of observations; the displayed value (winning_values) is reconciled from those observations by explicit source-priority rules. This is a golden-record / MDM model.

6.3 winning_values — the reconciled display layer

The reconciler picks one winner per attribute (per scope) into winning_values. Its exact shape is pinned by the generated columns (verbatim, 0009_…generated_columns.sql):

  ADD COLUMN gen_gtin  TEXT            GENERATED ALWAYS AS (identity->>'gtin')  STORED,

  ADD COLUMN gen_inventory_total INT   GENERATED ALWAYS AS ((winning_values #>> '{inventory,_primary,total}')::int) STORED,

CREATE INDEX idx_catalog_products_gen_brand ON catalog_products (gen_brand) WHERE gen_brand IS NOT NULL;
CREATE INDEX idx_catalog_products_gen_gtin  ON catalog_products (gen_gtin)  WHERE gen_gtin  IS NOT NULL;
CREATE INDEX idx_catalog_products_gen_brand_price ON catalog_products (gen_brand, gen_primary_price);
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_catalog_products_gen_title_trgm ON catalog_products USING GIN (gen_title gin_trgm_ops);
CREATE INDEX idx_catalog_products_values_gin     ON catalog_products USING GIN (values);

So winning_values looks like:

{
  "title":     { "_primary": { "value": "Google Pixel 10 5G …", "source": "croma:link", "confidence": 0.95 } },
  "pricing":   { "_primary": { "currency": "INR", "tiers": [ { "amount": 79999 } ] } },
  "inventory": { "_primary": { "total": 12 } }
}

Identity (gtin/brand) lives in the separate identity JSONB, projected to gen_brand/gen_gtin for indexed search; price/inventory winners are denormalized into side tables (§9.4–9.5).

PART 2 — Current system HLD (deep technical)

8. Stage-by-stage data flow (link path, the most complex)

Stage 1 — Fetch escalation (packages/link-adapter/src/fetch-escalation.ts)

Static HTTP → headless browser (ingestion-browser-fallback) if anemic (HTML < ~5 KB, anti-bot markers, or missing structured data) → unblock vendor (ingestion-antibot-vendor, ScrapingBee) within a per-URL cost ceiling.

Stage 2 — Extraction layers (packages/link-adapter/src/extract-layers.ts)

Priority-ordered; each emits ExtractedFact[]:

Layer What Conf
G — Per-site parser Croma/Amazon/Walmart/BestBuy/eBay 0.80–1.0
A — Structured JSON-LD, microdata, OpenGraph, Next/Nuxt/Shopify/Woo/Magento ~0.95
B — DOM heuristics itemprop/class-name price, title, images, breadcrumb 0.65–0.9
C — LLM gap-fill fills only still-missing fields ~0.7
F — Vision screenshot → vision model ~0.70

ExtractedFact (verbatim, packages/ingestion/field-extractor/src/types.ts):

export interface ExtractedFact {
  rawKey: string;
  canonicalPath: string | null;        // null until the Semantic Mapper assigns it
  extractedValue: unknown;
  normalizedValue: unknown;
  unit: string | null;
  sourcePointer: string;               // JSONPath into raw_data, e.g. "$.variants[0].barcode"
  extractionMethod: "direct" | "computed" | "inferred";
  confidence: number;                  // 0..1, value correctness
  mappingMethod: string | null;
  mappingCandidates: Array<{ key: string; score: number; reason?: string }> | null;
  sourceAlternatives: Array<{ value: unknown; sourcePointer: string; confidence: number }> | null;
  approved: boolean;
}

Stage 3 — Semantic mapper (packages/ingestion/semantic-mapper)

rawKey → canonicalPath with a mapping score (channel-exact 0.40, synonym 0.18, type 0.10, unit 0.07, category 0.06, embedding 0.15 stubbed, tenant-override 0.04). Thresholds: ≥0.55 auto · 0.40–0.55 suggestion · <0.25 unmapped.

Stage 4 — Identity resolution (catalog-service/src/identity-resolver.ts)

GTIN exact (1.0) → MPN+brand exact (0.9) → merchant SKU exact-or-none (1.0, skips fuzzy) → fuzzy brand+title via multi-source-reconciler (≥0.7 auto / 0.5–0.7 review / else new).

Stage 5 — Readiness gate (catalog-service/src/gate/evaluate-gate.ts)

CANONICAL_MINIMUM (verbatim, canonical-minimum.ts):

export const CANONICAL_MINIMUM = [
  "title", "brand", "pricing.primary", "category_path", "identifier"
] as const;  // identifier = gtin OR mpn OR primary_identifier; price is non-fillable in v1

admit = all five present AND no blocking signal.

Stage 6 — Policy detectors (packages/ingestion/policy-engine/router.ts)

Nine detectors (low-confidence-mapping, missing-required-attribute, field-conflict, unit-conflict, potential-duplicate, category-ambiguous, variant-incomplete, price-anomaly, value-contradiction) → any blocking signal routes to review.

Stage 7 — Admit or stage (admit-or-stage.ts)

Admit → catalog write. Fail/ambiguous → staged_products (the Lab queue).

Stage 8 — Anomaly Lab (aonex-frontend/.../ingestion/anomaly-lab, API apps/api/.../anomaly-lab.ts)

Reviewer fills title/brand/category_path/identifier (price NOT fillable today), re-runs the gate, promotes; or links to an existing product (skips the gate); or rejects.

Stage 9 — Catalog write + reconciliation + identity policy

catalog-write.ts appends observations into values; the reconciler computes winning_values; identity-policy.ts guards identity mutations (strength<0.7 freeze; gtin/mpn conflict freeze; brand needs 3 consecutive priority-1 obs; auto-unfreeze after 5).

11. Why clients say competitors are superior (the diagnosis)

  1. The 5-field AND-gate is binary, uniform, and price is non-fillable → valid-but-incomplete products dead-end; a reviewer who can see the price can't enter it.
  2. Extraction breaks silently at commerce-critical fields (a missed @graph JSON-LD shape cascades into "missing brand/price/identifier"); category confidence is hardcoded to 0.
  3. The catalog is schema-agnostic — no notion of product kind; the global gate is the only enforcement, applied identically to a phone and a medicine.
  4. Source URL and reviews are second-class (URL is ingestion metadata; reviews are a scalar).
  5. Identity only fires on a present GTIN — which extraction rarely captures — so the same product across marketplaces duplicates.

PART 3 — Target design (after phases −1 → 4)

13. End-state schema deltas (verbatim target DDL)

13.1 Multi-identifier set + concurrency guard (Phase 2)

ALTER TABLE catalog_products
  ADD COLUMN identifiers       jsonb   NOT NULL DEFAULT '[]'::jsonb,  -- typed identifier set
  ADD COLUMN identifier_exists boolean NOT NULL DEFAULT true,         -- escape hatch
  ADD COLUMN pipeline_version  integer NOT NULL DEFAULT 1;            -- old=1, new=2 (anti-dup)
CREATE INDEX idx_catalog_products_identifiers
  ON catalog_products USING gin (identifiers jsonb_path_ops);         -- match-on-any, indexed

-- DB-enforced single winner on a strong key (concurrency / anti-duplication)
CREATE TABLE product_strong_identifiers (
  tenant_id uuid NOT NULL, identifier_type text NOT NULL, identifier_value text NOT NULL,
  product_id uuid NOT NULL REFERENCES catalog_products(product_id),
  PRIMARY KEY (tenant_id, identifier_type, identifier_value)
);

identifiers[] element shape (TS):

interface Identifier {
  type: "gtin"|"upc"|"mpn"|"asin"|"shopify_gid"|"ebay_id"|"merchant_sku";
  value: string;
  source: string;          // "connector:shopify" | "link:croma" | "backfill:icecat"
  corroborated?: boolean;  // backfill→strong ONLY via promoteBackfill (≥2 providers + round-trip)
}
// strength: gtin/upc/mpn = strong; asin/shopify_gid/ebay_id = namespace; merchant_sku = tenant;
//           backfill & !corroborated = weak. Auto-merge requires a shared STRONG key + no variant conflict.

13.2 Archetype model (Phase 1) — family finally wired

type AttributeTier = "required" | "recommended" | "optional";
interface AttributeSpec { field: string; tier: AttributeTier; weight: number; } // weighted (D4)
interface Archetype   { id: string; label: string; attributes: AttributeSpec[]; }
// e.g. smartphone: base_price/currency/identifier weight 1; title/brand 0.8; category 0.6; images 0.4 …
// catalog_products.family = classifyArchetype(category, title, brand); completeness scored per archetype.

Completeness = Σ weight(present required) / Σ weight(all required), per channel; admit when hardFloorOk (title + identity-or-escape-hatch) AND score ≥ publishThreshold.

13.3 GTIN backfill (Phase 2) — corroboration, formally

corroborated=true is set by one path (promoteBackfill): the same {type,value} from ≥2 independent providers AND a round-trip match (brand equals ours, title token-overlap ≥0.6). Candidates may key a new product immediately; they may merge two existing products only once strong. Conflicting higher-authority strong value → demote + freeze + review.

13.4 Normalized reviews (Phase 4)

CREATE TABLE catalog_reviews (
  review_id   uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  product_id  uuid NOT NULL REFERENCES catalog_products(product_id),
  source      text NOT NULL, author text, rating numeric(3,2) NOT NULL, body text,
  reviewed_at timestamptz, dedupe_key text NOT NULL, created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (product_id, dedupe_key)            -- cross-source dedupe
);

Cross-source rating = count-weighted mean over per-source aggregates. Source URL is emitted as a source_url canonical observation → reconciled into winning_values.source_url → displayed.

13.5 Eval & calibration (Phase −1) — the measurement substrate

New @aonex/ingestion-eval: a labeled golden set (regression + rotating holdout), weighted field precision/recall, the north metric (auto-promote precision) + guardrail (auto-promote rate), a CI gate, and a bridge feeding @aonex/calibration (isotonic + beta-binomial) so confidence becomes empirical, not arbitrary.

15. Locked decisions, tradeoffs & SLOs (governing the build)

  • D1 Measurement before mechanism · D2 strong-key-or-Lab · D3 backfill promotion rule · D4 one vertical / weighted completeness / new-ingests / we own the taxonomy · D5 anti-dup by reading + heal-on-touch, not migrating.
  • Tradeoffs: lower auto-promote rate early (precision first); higher per-URL cost on the long tail, capped.
  • SLOs: Lab load ≤35% (alarm 50%, target 15%); shippable-at-scale ≥70% auto-promote at ≥98% precision; weekly drift job; cost-cap → budget_truncated partial, never silent drop.
  • Lab capacity: ~2 FTE at 35% of ~5k/day, trending <1 FTE at 15%; Lab decisions feed calibration + the eval holdout (a training source, not a sink).

16. End-state "day in the life"

  1. A client pastes a Walmart URL for a product on a site we have no parser for. The generic extractor fills 18 fields; no GTIN, so backfill resolves one from brand+model; that GTIN matches an existing Shopify-sourced product → we attach a Walmart-channel observation, not a duplicate. Completeness 94% for smartphone → auto-promoted, no human touch.
  2. A handmade candle (CSV, no GTIN) gets identifier_exists=false, scores 80% for home-fragrance → published, no false "missing identifier" block.
  3. An ambiguous listing lands in the Lab at 76%, one missing attribute + an unparsed price. A reviewer types the price, accepts the suggested category, promotes in ten seconds — and that decision trains the calibrator.

18. Glossary

  • Observation — one source's claim about one attribute at one time, with confidence.
  • values (4-axis) — [attribute][channel|_unscoped][locale|_unscoped] → Observation[].
  • winning_values — reconciled, displayed value per attribute (projected to generated columns).
  • AdapterOutput — the normalized output every source adapter emits.
  • CANONICAL_MINIMUM — today's five hard-required gate fields.
  • Archetype / family — product type defining tiered, weighted required attributes. (Target.)
  • Completeness score — weighted % of an archetype's required attributes present, per channel.
  • Multi-identifier / strong-key-or-Lab — typed identifier set; auto-merge only on a shared strong corroborated key, else a Lab merge proposal. (Target.)
  • GTIN backfill — resolving a missing GTIN from external registries; candidate→strong on corroboration. (Target.)
  • Golden record — the single reconciled catalog_products row for one physical product.
